Subscribing: onDirty

Once the boss fight starts, the BossBar at the top of the screen has to follow the boss's health. Health changes in the damage event; the BossBar lives somewhere else. The two need a way to talk.

When a menu uses a Signal, Sparrow UI subscribes for you and you never need this page. For things outside menus, such as BossBars, logs, or scoreboards, you subscribe yourself.

What onDirty does​

onDirty(listener) registers a listener that is called whenever the Signal's value may have changed. It returns a Subscription: keep it and the notifications keep coming, call close() and they stop.

The listener takes no arguments. Call get() inside it when you need the new value.

Making a BossBar follow health​

public final class BossHealthBar {
    private final BossBar bar;
    private final Subscription subscription;

    public BossHealthBar(Signal<Integer> health, int maxHealth) {
        this.bar = BossBar.bossBar(
                Component.text("Ancient Guardian"), 1f,
                BossBar.Color.RED, BossBar.Overlay.PROGRESS
        );
        // Every health change updates the bar proportionally
        this.subscription = health.onDirty(() -> {
            float progress = health.get() / (float) maxHealth;
            this.bar.progress(Math.clamp(progress, 0f, 1f));
        });
    }

    public BossBar bar() {
        return this.bar;
    }

    // Call when the boss dies or is removed
    public void close() {
        this.subscription.close();
    }
}

BossBar and Component come from Adventure. The Subscription sits in a field and stays valid for as long as the boss lives.

Caveats​

Keep the Subscription

A Signal only holds its subscribers weakly. If nothing holds the Subscription returned by onDirty, it may be garbage collected and the listener quietly stops, with no error.

A notification only means "may have changed"

Notifications carry no value. get() in the listener reads whatever is current, so with several threads writing in a row, an intermediate value may never be seen, and two notifications may read the same value.

So do not use the listener for bookkeeping. To record every hit the boss takes, record it where the damage is dealt, not by working backwards from health changes.

The listener runs on the writing thread

Whichever thread changes the health runs the listener. With several writing threads, the listener may run concurrently.

Listeners should be thread safe and return quickly, and must not change the same Signal again.

For keeping and cleaning up subscriptions, see Lifecycle and cleanup. For how menus manage subscriptions automatically, see Signals in the UI.
