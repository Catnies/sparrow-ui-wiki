异步加载

玩家打开商店时，菜单需要显示账户余额，但余额保存在数据库里，查询可能要花几百毫秒。我们希望菜单先显示「加载中」，查询完成后再显示余额；期间读取菜单状态的代码可以继续执行。

本页围绕这个过程使用 Signal.async，随后演示发放奖励后如何重新查询。把状态用于物品名称和窗口显示的接法放在绑定到 UI，这里先通过控制台观察结果。

打开商店时查询余额​

假设插件已经有一个经济服务 economy，它的 loadBalance(UUID) 会查询数据库并返回玩家余额，单位为金币。这是业务代码提供的方法，需要替换为项目实际使用的经济 API，Sparrow UI 不负责连接数据库。

下面的代码放在处理打开商店请求的位置。viewer 是打开菜单的玩家，ioExecutor 是插件已经创建并复用的后台 I/O 执行器。为了说明显示过程，假设这名玩家在数据库中的余额为 100。

UUID playerId = viewer.getUniqueId();
AsyncSignal<Long> balance = Signal.async(
        (Long) null,
        ioExecutor,
        () -> economy.loadBalance(playerId)
);

Signal<String> balanceText = balance.map(value ->
        value == null ? "加载中…" : "余额：" + value);

Subscription subscription = balanceText.onDirty(() ->
        System.out.println(balanceText.get()));
System.out.println(balanceText.get());

Signal.async 创建时就把查询提交给执行器。它的三个参数分别是首次结果返回前的占位值、执行查询的执行器，以及实际查询函数。函数捕获的是 UUID，后台任务无需保留玩家对象。

查询还没完成时，balance.get() 返回 null，balanceText.get() 返回「加载中…」。查到余额后，Signal 保存 100 并通知依赖者，回调读取的文字变成「余额：100」。查询如果已经完成，首次读取就会直接得到余额；不能依赖程序一定先输出「加载中…」。

这里把首次读取与订阅都写出来，是因为 onDirty 不会立即回放当前值。示例中的控制台订阅只用于观察变化，结束观察时应调用 subscription.close()；实际菜单的绑定方式见绑定到 UI。

用 null 作占位值，是为了区分「还没查到」和「余额为零」。如果业务允许先显示零，也可以传 0L。占位值和查询结果都允许为 null，含义由业务决定。

默认使用 Objects.equals 比较新旧余额，相同的结果不会再次通知。需要自定义判等时，可在 Signal.async 的最后一个参数传入 sameValue，规则见基础用法。

发放奖励后刷新余额​

玩家领取了一笔 50 金币的奖励，数据库中的余额从 100 变成 150。之前的 balance 仍保存着旧结果，我们需要让它再查一次。

下面接着使用上一节的 playerId、balance 和 ioExecutor。假设领取资格已经由业务层确认，economy.deposit(playerId, 50L) 会写入数据库，并在提交成功后返回。这段代码应放在奖励发放流程中。

ioExecutor.execute(() -> {
    economy.deposit(playerId, 50L);
    // 数据库提交成功后, 再读取新的余额.
    balance.dirty();
});

AsyncSignal 的值由查询函数提供，因此刷新时调用 dirty()，让它重新执行 () -> economy.loadBalance(playerId)。它不提供 set 或 update。

重新查询期间，get() 继续返回上一次的结果，不会退回“加载中”。例如余额已经查到 100，刷新时仍显示 100，直到新结果替换它。

同一个 Signal 的查询不会并行执行。如果查询还没结束就调用了 dirty()，它会记下“完成后再查一次”；这期间连续调用多次，也只补一次查询。

例如，第一笔奖励发放后正在查询余额，第二笔奖励又已提交。这时再次刷新，便会在本轮完成后补查。

时刻操作可读取的值
已加载上次查到余额 100100
开始刷新调用 dirty()，提交查询 A100
A 尚未完成再调用两次 dirty()，登记一次补查100
A 完成发布结果 150，提交查询 B150，直到 B 完成
B 完成发布结果 200200

本轮结果仍会发布，即使已经登记了补查。dirty() 不会取消本轮查询，也不会把它的结果当作过期数据丢掉。若正在按搜索词切换查询来源，可以结合上一页的 switching 选择当前来源，避免把不同搜索词的结果写进同一个状态。

不要在查询函数里刷新自己

查询函数不能直接或间接调用自身 Signal 的 dirty()，否则会抛出 IllegalStateException。刷新应由写入完成、用户操作或轮询触发。

查询与通知的线程

查询函数应只处理数据库、网络请求或线程安全的数据，避免在后台查询中读取玩家背包、操作世界等需要所属线程的 Bukkit 状态。

加载完成后的失效通知也从执行查询的线程发出。手动注册的 onDirty 回调不会自动切到玩家线程；回调需要操作玩家或世界时，应另行调度到相应线程。

查询函数抛出 RuntimeException，或执行器拒绝任务时，异常会交给 Sparrow UI 的异常处理器，已保存的值保持不变。第一次查询失败时仍保留占位值；之后可以再次 dirty() 重试。占位值本身无法区分“加载中”和“加载失败”，需要展示错误状态时，应让业务层提供相应的状态值。
