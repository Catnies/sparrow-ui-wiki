Signal 派生

购买按钮可能同时依赖数量、单价和余额；切换分类后，菜单又要改为读取另一份数据。派生 Signal 可以组合这些来源，也可以控制变化通知的时机。

组合多个值​

Signals.combine 接受两个或三个 Signal。任意来源变化，组合结果就会通知下游；真正读取结果时，再取各来源的当前值进行计算。

下面用两个来源计算总价，再用三个来源判断能否购买：

MutableSignal<Integer> quantity = Signal.of(2);
MutableSignal<Integer> price = Signal.of(30);
MutableSignal<Integer> coins = Signal.of(100);

Signal<Integer> total = Signals.combine(quantity, price,
        (amount, unitPrice) -> amount * unitPrice);
Signal<Boolean> affordable = Signals.combine(quantity, price, coins,
        (amount, unitPrice, balance) -> (long) amount * unitPrice <= balance);

System.out.println(total.get());
System.out.println(affordable.get());
quantity.set(4);
System.out.println(total.get());
System.out.println(affordable.get());

初始总价为 60，余额足够；数量改成 4 后，总价变成 120，余额不足。下面的演示使用同样的初始值。修改余额时，总价不受影响；修改数量或单价时，两项结果都需要重新计算。

购买预览

combine 与 map 一样按需计算并缓存结果，不比较新旧结果是否相同。余额从 100 变成 150 时，即使仍然买得起，affordable 也会通知下游。需要过滤重复结果，可以再接 .mapDistinct(value -> value)。

多个来源分别读取

组合函数可能在任意读取线程执行，应只计算结果。多个来源的读取不构成一次原子快照；依次修改数量和单价时，读取方可能看到其中一项已更新、另一项尚未更新。

如果两个字段必须一起变化，把它们放进同一个不可变对象，用一次 update 替换，随后通过 map 或 lens 读取字段。

单独读写一个字段​

MutableSignal.lens 从一个对象中取出字段，返回可读写的 MutableSignal。第一个函数读取字段，第二个函数用新字段值创建新的完整对象。

record Settings(boolean sound, int volume) {}

MutableSignal<Settings> settings = Signal.of(new Settings(true, 5));
MutableSignal<Integer> volume = settings.lens(
        Settings::volume,
        (current, value) -> new Settings(current.sound(), value));

volume.set(8);
System.out.println(settings.get());

settings.update(current -> new Settings(false, current.volume()));
System.out.println(volume.get());

写入 volume 后，完整设置变为 Settings[sound=true, volume=8]。随后关闭声音，volume.get() 仍然是 8，依赖音量的订阅者也不会因为声音开关变化而收到通知。

写入 lens 会调用原 Signal 的原子更新，第二个函数应保留当前对象中未修改的字段。volume.update(value -> value + 1) 也可以使用。需要自定义字段的相等规则时，将 sameValue 作为第三个参数传入。

字段转换函数可能重试

两个函数都应无副作用，写入函数返回新对象，不修改传入对象。它们可能在不同线程执行，也可能因为并发更新而重试。不要在函数中捕获玩家、世界或窗口对象。

跟随当前选择​

武器和护甲各有一份库存，菜单只显示当前分类。用 Signals.switching 将分类 Signal 作为选择条件，返回值就会跟随选中的来源。

MutableSignal<Integer> weapons = Signal.of(5);
MutableSignal<Integer> armor = Signal.of(8);
MutableSignal<String> category = Signal.of("weapons");

Signal<Integer> currentStock = Signals.switching(
        Map.of("weapons", weapons, "armor", armor), category);

System.out.println("初始库存：" + currentStock.get());
try (Subscription subscription = currentStock.onDirty(() ->
        System.out.println("当前库存：" + currentStock.get()))) {
    armor.set(7);
    category.set("armor");
    weapons.set(4);
    armor.set(6);
}

初始库存为 5，回调依次输出 7、6。选中武器时，护甲的变化不向下游传递；切到护甲后，武器的变化也不再影响当前结果。切换分类会读取新来源的最新值。

传入的 Map 会被复制，之后修改原 Map 不会增加可选来源。Map 必须非空，分类值必须对应其中的 key；找不到来源时会抛出 IllegalArgumentException。

已有 KeyedSignal 时，也可以写成 Signals.switching(source, category)，读取当前 key 对应的分区。分区的创建与管理看 分区状态。

跟随会增减的成员​

统计多个仓库的库存时，仓库本身的数量也可能变化。Signals.merging 同时跟踪成员列表和列表中每个成员的 Signal，新增成员后开始监听，移除后解除监听。

下面用三个独立库存演示。members 决定哪些库存参与统计：

MutableSignal<Integer> apples = Signal.of(5);
MutableSignal<Integer> books = Signal.of(3);
MutableSignal<Integer> gems = Signal.of(10);
MutableSignal<List<MutableSignal<Integer>>> members = Signal.of(List.of(apples, books));

Signal<Long> changed = Signals.merging(members, member -> member);
Signal<Integer> total = changed.map(ignored ->
        members.get().stream().mapToInt(Signal::get).sum());

System.out.println("初始总数：" + total.get());
try (Subscription subscription = total.onDirty(() ->
        System.out.println("当前总数：" + total.get()))) {
    apples.set(4);
    members.set(List.of(books, gems));
    apples.set(0);
    gems.set(9);
}

初始总数为 8，回调依次输出 7、13、12。苹果库存移出列表后，再修改它不会触发统计更新。

merging 返回的 Long 只是递增的变化标记，不是成员数量，也不是库存合计。这里用 map 在标记变化后重新求和，成员的依赖关系已由 merging 建立。

如果列表中放的是业务对象，第二个参数改为读取该对象的 Signal，例如 Warehouse::stock。应返回成员已有的 Signal，成员集合的遍历顺序也应保持稳定。普通 MutableSignal<List<T>> 要通过 set 发布新列表；ListSignal、SetSignal 也可以直接作为成员来源，用法看 集合状态。

等输入停下来再更新​

搜索框里连续输入 d、di、diamond 时，通常只需要处理最后一个完整搜索词。debounce(5) 会从最后一次变化起等待 5 tick，期间再次变化就重新等待。

下面的方法接收输入 Signal，返回这次监听的 Subscription：

public static Subscription watchSearch(Signal<String> input) {
    Signal<String> settled = input.debounce(5).mapDistinct(String::strip);
    return settled.onDirty(() -> System.out.println("搜索词：" + settled.get()));
}

将输入框的文本写入原始 Signal，settled 就会在输入停顿后更新。保存返回的订阅，并在搜索结束时关闭。空格由 strip 去掉，处理后的文本相同则不重复通知。

有订阅期间，等待中的 settled.get() 仍返回上一次通知时的值。需要立即取得输入框内容时，读取原始 input。如果持续输入而没有停顿，防抖也会持续等待。

用毫秒计时则改为 input.debounceMillis(250)。tick 版跟随服务器 tick，5 tick 只在 20 TPS 时约等于 250 毫秒。

定时派生需要订阅

防抖和节流只有在存在订阅者时才安排定时任务。仅创建派生 Signal 再调用 get()，会直接读到上游当前值，不会等待。最后一个订阅关闭后，待执行的延时任务也会取消。

使用定时 API 前应已完成 Sparrow UI 初始化。tick 版的延时回调在全局区域调度线程执行，毫秒版在 Paper 异步调度线程执行；不要在回调里直接操作玩家或方块。异步查询的用法看 异步加载。

限制连续更新的频率​

进度持续变化时，如果用防抖，可能一直等不到停顿。throttle(5) 会先通知一次，之后两次通知之间至少间隔 5 tick；期间的变化合并到下一次通知，读取当时的最新值。

public static Subscription watchProgress(Signal<Integer> progress) {
    Signal<Integer> limited = progress.throttle(5);
    return limited.onDirty(() -> System.out.println("进度：" + limited.get()));
}

假设初始值为 0，已经建立订阅，随后发生以下变化，且延时任务按期执行：

时间操作debounce(5)throttle(5)
tick 0写入 10等待通知 10
tick 2写入 20重新等待暂不通知
tick 4写入 30重新等待暂不通知
tick 5没有新写入继续等待通知 30
tick 9没有新写入通知 30不通知

节流在间隔内仍返回上次通知时的值，原始 Signal 则可以读到最新值。补发通知也会开启下一个间隔；期间没有新变化，就不会继续通知。毫秒版写作 progress.throttleMillis(250)。

节流回调可能来自不同线程

立即通知发生在上游变化的线程，延迟补发发生在对应的调度线程。debounce、throttle 及其毫秒版本的间隔都必须大于 0，否则抛出 IllegalArgumentException。

定时回调会读取上游。若上游包含 map，它的计算也可能在这个线程执行，所以整段计算都应简短，不做耗时 I/O。

用时钟驱动倒计时​

时钟 Signal 定期通知依赖它的地方，适合倒计时、冷却显示等需要持续刷新的内容。

API通知间隔get() 的值
Signals.ticking()每 tick时钟运行期间累计的 tick 数
Signals.everyTicks(20)每 20 tick累计经过的 20 tick 周期数
Signals.everyMillis(1000)每 1000 毫秒该毫秒时钟累计经过的周期数

下面在当前计数的基础上，倒数 10 个周期。初始剩余值为 10，每经过一个周期减一：

public static Subscription watchCountdown() {
    Signal<Long> clock = Signals.everyTicks(20);
    long start = clock.get();
    Signal<Long> remaining = clock.mapDistinct(value -> Math.max(0L, 10L - (value - start)));

    System.out.println("剩余：" + remaining.get());
    return remaining.onDirty(() -> System.out.println("剩余：" + remaining.get()));
}

计数到 0 后，mapDistinct 会过滤重复的 0。结束使用时仍需关闭返回的订阅，时钟不会因为倒计时到零而自动退订。

同周期的时钟由多个使用者共享。第一个订阅者到来时启动，最后一个离开时停止；重新订阅后从原计数继续。所以 get() 不是当前时间，也不是当前玩家打开菜单的时长。若时钟已经运行，新订阅会使用现有计时，第一次通知可能不到 20 tick 就到达。

计时单位与线程

tick 时钟在服务器变慢时也会变慢。需要按现实时间判断是否到期时，应保存独立的截止时间，用时钟通知驱动显示刷新。

everyTicks 的周期必须为正数，everyMillis 至少为 50 毫秒。tick 时钟从全局区域调度线程通知，毫秒时钟从异步线程通知，都不代表当前玩家的实体线程。
